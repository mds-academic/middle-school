Mengenal Authentication

Saat memakai aplikasi atau perangkat tertentu, user kadang diminta memasukkan PIN, password, sidik jari, atau kode akses. Proses pemeriksaan inilah yang disebut authentication.

Di project Brankas Digital, authentication dibuat dalam versi paling sederhana: aplikasi membandingkan PIN yang diketik user dengan PIN contoh yang sudah ditentukan.

Versi project kita

  • User mengetik PIN di txtPIN.
  • User menekan tombol LOGIN.
  • Aplikasi mengecek apakah txtPIN.Text = "1234".
  • Aplikasi menampilkan status sesuai hasil pengecekan.

Walaupun sederhana, konsep ini menjadi dasar untuk memahami aplikasi yang membutuhkan izin akses.

Perhatikan bahwa aplikasi tidak langsung memberi akses. Aplikasi harus mengecek dulu isi input. Inilah alasan kita membutuhkan kondisi.

PIN dan Data Pribadi

PIN berarti Personal Identification Number. Dalam kehidupan nyata, PIN termasuk informasi pribadi. PIN membantu mencegah orang lain mengakses perangkat, aplikasi, atau layanan tertentu.

Karena PIN bersifat rahasia, kita tidak boleh meminta teman menyebutkan PIN asli, dan tidak boleh memakai PIN pribadi di project latihan.

Perbedaan penting

  • PIN dummy: contoh untuk latihan, boleh ditampilkan di project.
  • PIN pribadi: kode akses asli, tidak boleh dibagikan atau ditulis di project.

Di kelas ini, semua contoh PIN hanya dipakai untuk memahami alur aplikasi dan kondisi if-then-else.

Membedakan PIN Mudah Ditebak

PIN seperti 1234, 0000, atau angka berulang mudah ditebak karena polanya terlalu jelas. Tanggal lahir juga sebaiknya dihindari karena bisa diketahui orang lain.

Aktivitas ini tidak meminta kalian membuat PIN asli. Kita hanya sedang melatih cara berpikir tentang keamanan digital.

Ciri PIN yang lemah

  • Urutan angka terlalu umum, seperti 1234.
  • Semua digit sama, seperti 0000 atau 1111.
  • Menggunakan tanggal lahir atau angka yang mudah diketahui.
  • Terlalu sering dipakai untuk banyak akun.

Untuk project App Inventor, tetap gunakan PIN dummy agar aman dan mudah diuji.

Aplikasi Mulai Mengambil Keputusan

Sebelumnya kalian sudah membuat aplikasi yang merespons tombol atau menampilkan pesan. Di sesi ini, aplikasi tidak hanya melakukan satu aksi. Aplikasi harus memilih respons berdasarkan kondisi.

Kondisinya adalah: apakah teks yang diketik di txtPIN sama dengan "1234"?

Dua cabang

  • Jika kondisi bernilai true, aplikasi menjalankan bagian then.
  • Jika kondisi bernilai false, aplikasi menjalankan bagian else.

Satu input hanya masuk ke satu cabang. Jadi, saat PIN salah, aplikasi tidak boleh sekaligus menampilkan “Akses diterima”.

Memahami If-Then-Else

If-then-else membantu aplikasi memilih satu dari dua tindakan. Di App Inventor, bentuknya berupa blok kontrol berwarna kuning/cokelat, lalu di dalamnya ada bagian kondisi, then, dan else.

Di project ini, kondisi membaca isi txtPIN.Text. Kalau isi teksnya sama dengan "1234", aplikasi mengubah lblStatus.Text menjadi “Akses diterima”. Kalau tidak sama, bagian else yang berjalan.

Cara membaca

IF = bagian yang dicek. THEN = aksi saat benar. ELSE = aksi saat salah.

Jangan tertukar: else tidak membutuhkan kondisi baru untuk project ini. Else berarti “selain kondisi yang benar tadi”.

Membaca Hasil Perbandingan

Operator = pada Blocks App Inventor dipakai untuk membandingkan dua nilai. Hasilnya bukan angka, tetapi nilai logika: true atau false.

Jika txtPIN.Text berisi “1234”, hasil perbandingannya true. Jika berisi nilai lain, hasilnya false.

Contoh

txtPIN.Text = "1234" bukan berarti mengisi TextBox dengan 1234. Di sini, tanda sama dengan digunakan untuk mengecek apakah isi TextBox sudah sama dengan teks 1234.

Kesalahan yang sering terjadi adalah membandingkan komponen txtPIN langsung, bukan property txtPIN.Text. Yang kita butuhkan adalah isi teksnya.

Alur Project Brankas Digital

Project ini bisa dibaca dengan pola Input -> Event -> Condition -> Output. Pola ini membantu kalian menyusun blok secara terarah.

Inputnya adalah teks yang diketik user. Event-nya adalah tombol LOGIN diklik. Condition-nya adalah perbandingan isi txtPIN.Text dengan PIN dummy. Output-nya adalah teks status pada lblStatus.

Pola lengkap

txtPIN.Text masuk -> btnLogin.Click berjalan -> if txtPIN.Text = "1234" dicek -> lblStatus.Text berubah.

Kalau project tidak berjalan, gunakan pola ini untuk menelusuri bagian mana yang belum tepat.

  3. Aplikasi membandingkan input dengan PIN dummy.
  4. Aplikasi memilih pesan yang tepat.

Setelah alur ini jelas, bentuk Blocks akan lebih mudah dipahami.

Event btnLogin.Click

Event adalah pemicu. Pada project ini, event yang dipakai adalah btnLogin.Click. Artinya, blok di dalamnya berjalan ketika user menekan tombol LOGIN.

Jika kondisi diletakkan di luar event, aplikasi tidak tahu kapan harus memeriksa PIN. Jika event yang dipakai salah, tombol LOGIN bisa terlihat ada, tetapi tidak melakukan apa-apa.

Debug awal

Kalau tombol ditekan tetapi status tidak berubah, cek dulu apakah blok utama yang dipakai benar-benar when btnLogin.Click.

Event ini adalah wadah. Di dalamnya baru kita masukkan if-then-else.

Property Text pada TextBox

TextBox adalah komponen. Isi yang diketik user berada di property Text. Jadi, saat ingin membaca input user, kita memakai txtPIN.Text.

Ini salah satu bagian yang sering membuat bug. Siswa kadang membandingkan txtPIN langsung dengan “1234”. Padahal yang perlu dibandingkan adalah teks di dalamnya.

Analogi

TextBox seperti kotak. Kita tidak membandingkan kotaknya dengan PIN. Kita membandingkan isi kotaknya.

Dengan membaca property yang tepat, kondisi akan mendapat data yang benar untuk dibandingkan.

Comparison di App Inventor

Operator = pada bagian Logic digunakan untuk membandingkan dua nilai. Di project ini, nilai kiri adalah txtPIN.Text, dan nilai kanan adalah text block "1234".

Hasil dari perbandingan ini menentukan bagian mana yang dijalankan oleh if-then-else.

Perhatikan tipe data

Di TextBox, input user dibaca sebagai teks. Karena itu, PIN contoh juga ditulis sebagai text block “1234”, bukan math number 1234.

Untuk latihan ini, menggunakan text block membuat perbandingan lebih sesuai dengan isi TextBox.

Bagian THEN

Bagian then berisi perintah yang dijalankan kalau kondisi benar. Dalam project Brankas Digital, kondisi benar berarti user memasukkan PIN dummy yang sesuai, yaitu “1234”.

Perintah yang dijalankan adalah mengubah lblStatus.Text menjadi “Akses diterima”.

Kenapa pakai lblStatus?

Karena project ini menampilkan hasil langsung di layar utama. Label status membantu user melihat apakah login berhasil atau perlu mencoba lagi.

Pastikan teks status ditulis dengan benar agar output sesuai test case.

Bagian ELSE

Bagian else menangani semua kondisi yang tidak memenuhi syarat. Di sini, syaratnya hanya satu: input harus sama dengan “1234”.

Jadi, input seperti “0000”, “1235”, “abcd”, atau input kosong akan masuk ke bagian else. Output-nya adalah “PIN salah. Coba lagi.”

Kesalahan umum

Beberapa siswa hanya membuat bagian then tanpa else. Akibatnya, saat PIN salah, aplikasi tidak memberi respons yang jelas. Padahal project ini perlu dua kemungkinan output.

Dengan else, user tahu bahwa PIN yang dimasukkan belum sesuai.

Membaca Blocks Lengkap

Rangkaian lengkap project ini terdiri dari satu event, satu kondisi, dan dua output. Kalau dibaca sebagai kalimat: ketika tombol Login diklik, jika isi txtPIN sama dengan 1234 maka tampilkan Akses diterima, selain itu tampilkan PIN salah.

Kalimat ini membantu kalian mengecek apakah blok sudah masuk akal sebelum diuji di AI2 Companion.

Cara tracing

  1. Mulai dari event btnLogin.Click.
  2. Masuk ke kondisi txtPIN.Text = "1234".
  3. Tentukan hasil true atau false.
  4. Lihat cabang yang mengubah lblStatus.Text.

Kalau hasil testing tidak sesuai, tracing dari langkah 1 sampai 4.

Membaca Blocks tanpa Menjalankan

Reading Blocks berarti memprediksi perilaku aplikasi hanya dengan membaca blok. Skill ini penting karena membantu kalian menemukan bug lebih cepat.

Jika kalian bisa memprediksi output untuk input 1234 dan 0000, berarti kalian mulai memahami hubungan antara kondisi dan cabang.

Prediksi yang benar

  • Input 1234 -> kondisi true -> Akses diterima.
  • Input 0000 -> kondisi false -> PIN salah. Coba lagi.
  • Input kosong -> kondisi false -> PIN salah. Coba lagi.

Setelah memprediksi, baru buktikan lewat testing di aplikasi.

Testing dengan Expected Output

Testing bukan hanya menekan tombol sekali. Karena project ini punya dua cabang, kalian perlu membuktikan bahwa kedua cabang bekerja.

Minimal, uji satu PIN benar dan satu PIN salah. Jika keduanya sesuai expected output, logika utama sudah berjalan.

Jangan hanya test PIN benar

Kalau hanya mencoba 1234, kalian belum tahu apakah else bekerja. Bisa saja PIN salah tidak memberi respons, atau malah tetap diterima.

Input kosong bisa menjadi observasi tambahan untuk melihat bagaimana aplikasi menangani nilai yang tidak sesuai.

Menguji di Perangkat

AI2 Companion membantu kalian melihat aplikasi seperti user sungguhan. Setelah Blocks selesai, sambungkan project dan coba langsung dari perangkat atau emulator yang digunakan kelas.

Jangan mengubah Blocks di tengah testing hanya untuk membuat satu test case berhasil. Blok yang sama harus bisa menangani PIN benar dan PIN salah.

Checklist hasil

  • Status muncul setelah tombol LOGIN ditekan.
  • Status sesuai input yang diketik.
  • Aplikasi tidak menerima semua PIN.
  • Aplikasi tetap memberi respons saat input salah.

Jika ada output yang tidak sesuai, masuk ke debugging terarah.

Debugging Terarah

Kalau hasil tidak sesuai, jangan langsung menghapus semua blok. Mulai dari gejala, lalu cek bagian yang paling mungkin bermasalah.

Untuk project ini, bug umum biasanya ada di event, property Text, operator comparison, posisi then/else, atau label output yang salah.

Urutan cek yang aman

  1. Cek event btnLogin.Click.
  2. Cek apakah kondisi berada di dalam event.
  3. Cek apakah yang dibandingkan adalah txtPIN.Text.
  4. Cek apakah operatornya =.
  5. Cek apakah pesan THEN dan ELSE tidak tertukar.
  6. Cek apakah output mengubah lblStatus.Text.

Ubah satu bagian, lalu test lagi. Cara ini lebih aman daripada mengganti banyak blok sekaligus.

Common Misconception

Dalam project if-then-else, kode bisa terlihat benar sekilas, tetapi output tetap salah jika detail kecilnya tertukar.

Kesalahan paling umum adalah lupa bahwa input user berada pada property Text, bukan pada nama komponen. Selain itu, siswa kadang hanya membuat then tanpa else, sehingga aplikasi tidak memberi respons saat PIN salah.

Cara memperbaiki cara berpikir

Baca blok seperti kalimat. “Ketika tombol login diklik, jika isi txtPIN sama dengan 1234, maka status akses diterima, selain itu status PIN salah.” Jika kalimatnya tidak cocok dengan blok, berarti ada bagian yang perlu diperbaiki.

Biasakan juga bertanya: test case apa yang belum dicoba?

Data Aman dalam Project Login

Karena project ini bertema PIN, keamanan digital harus dibahas dengan jelas. Kalian tidak perlu dan tidak boleh memasukkan PIN asli ke project.

Data yang aman adalah data dummy: contoh yang dibuat untuk latihan. Data dummy boleh terlihat di layar, boleh dipakai untuk testing, dan tidak membuka akses ke akun apa pun.

Jangan pernah bagikan

  • PIN HP atau password aplikasi.
  • OTP dari SMS atau email.
  • Kode akses akun pribadi.

Jika ragu apakah sebuah data aman, jangan masukkan. Tanyakan guru terlebih dahulu.

Challenge ini tidak meminta keamanan tingkat lanjut. Fokusnya tetap membaca kondisi dan test case.
