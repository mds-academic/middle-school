Memahami Runtime Error

Runtime error terjadi ketika aplikasi sedang berjalan, bukan saat kita hanya melihat tampilan Designer. Jadi, aplikasi bisa terlihat baik-baik saja, tetapi tetap bermasalah saat digunakan.

Salah satu penyebabnya adalah aplikasi mencoba memproses data yang belum tersedia. Misalnya aplikasi menunggu angka, tetapi user belum mengisi TextBox.

Kenapa developer perlu peduli?

User bisa lupa mengisi kolom, salah mengetik, atau menekan tombol terlalu cepat. Aplikasi yang baik perlu memberi respons yang jelas, bukan membuat user bingung.

Di Sesi 9, kalian belajar membuat aplikasi yang lebih siap menghadapi situasi seperti itu.

Dalam project sungguhan, bentuk error bisa berbeda-beda. Kadang muncul pesan runtime error, kadang hasil tidak tampil, kadang aplikasi berhenti.

Hal yang perlu diamati

  • Apakah user mendapat petunjuk yang jelas?

Jawabannya akan menjadi alasan kenapa kita membutuhkan validasi input.

Perbedaan Setelah Validasi

Validasi membuat aplikasi lebih ramah untuk user. Aplikasi tidak langsung menjalankan proses saat data belum siap. Aplikasi memberi pesan terlebih dahulu agar user tahu apa yang perlu diperbaiki.

Project sample memakai pesan “TextBox tidak boleh kosong!” ketika txtInput.Text masih kosong.

Dua jalur aplikasi

  • Input kosong: tampilkan pesan peringatan.
  • Input terisi: lanjutkan proses dan tampilkan hasil.

Inilah pola yang nanti diterjemahkan ke Blocks menggunakan if - else.

Kosong Berbeda dari Nol

Ini bagian penting. Banyak orang mengira kosong dan 0 sama, padahal berbeda. Kosong berarti belum ada data. Angka 0 berarti ada data, yaitu nol.

Di App Inventor, input kosong biasanya dicek dengan membandingkan TextBox.Text dengan teks kosong: "".

Contoh

  • txtInput.Text = "" → kosong, tampilkan pesan.
  • txtInput.Text = "0" → terisi, lanjutkan proses.

Kalau aplikasi memperlakukan angka 0 sebagai kosong, hasilnya bisa salah untuk beberapa jenis aplikasi.

Cara Aplikasi Menangani Masalah

Error handling bukan berarti aplikasi tidak akan pernah mengalami masalah. Error handling berarti aplikasi disiapkan untuk memberi respons yang lebih baik ketika kondisi bermasalah muncul.

Pada project ini, kondisi yang ditangani adalah input kosong. Aplikasi mengecek dulu sebelum menjalankan proses berikutnya.

Pola sederhana

Jika input kosong, beri pesan. Jika input sudah ada, lanjutkan proses.

Pola ini akan sering dipakai saat membuat form, kalkulator, aplikasi catatan, dan aplikasi lain yang membutuhkan input user.

Validasi Sebelum Proses

Validasi membantu aplikasi menentukan apakah data sudah bisa dipakai. Tanpa validasi, aplikasi bisa mencoba memproses sesuatu yang belum ada.

Dalam project ini, validasinya sederhana: apakah txtInput.Text sama dengan teks kosong?

Kalau hasil cek benar

Artinya input masih kosong. Aplikasi menampilkan pesan “TextBox tidak boleh kosong!”.

Kalau hasil cek salah

Artinya input sudah terisi. Aplikasi boleh menjalankan proses di bagian else.

Kalian tidak perlu membuat validasi yang rumit dulu. Mulai dari satu kondisi yang paling sering terjadi: user lupa mengisi input.

Coba baca perilakunya

  3. Kalau input berisi angka lain, aplikasi masuk ke jalur normal dan menampilkan isi input.

Tiga tombol contoh di kiri—Kosong, 0, dan 42—dipakai untuk membantu kalian menguji tiga kondisi yang paling penting. Dengan begitu, kalian tidak menebak-nebak lagi saat masuk ke MIT App Inventor.

  • Apakah output muncul di area hasil yang benar?

Kalau perilaku UI di slide kiri sudah kalian pahami, barulah jauh lebih mudah untuk menerjemahkannya menjadi komponen di Designer dan logika if - else di Blocks.

Alur Project Detektif Crash

Project ini memakai alur yang singkat, tetapi sangat penting. Bukan menghitung rumus, melainkan mengecek dulu apakah data yang dibutuhkan sudah ada atau belum.

Pada slide kiri, alur itu disederhanakan menjadi Input → Check → Output. Ini membantu kalian melihat bahwa aplikasi yang baik tidak asal memproses semua hal, tetapi memeriksa kondisi lebih dulu.

Makna tiap bagian

  • Input: data yang diberikan user melalui txtInput.Text.
  • Check: aplikasi membandingkan apakah isi TextBox sama dengan teks kosong.
  • Output: jika kosong tampilkan pesan, jika terisi tampilkan hasil normal.

Kalau urutan ini tertukar, aplikasi bisa berperilaku aneh. Misalnya output langsung muncul tanpa pengecekan, atau aplikasi mencoba memproses data yang sebenarnya belum ada.

Ingat, sesi ini sedang melatih cara berpikir developer: sebelum memproses, cek dulu datanya siap atau belum.

Membaca Flowchart

Flowchart membantu kita membaca keputusan program tanpa harus melihat blok puzzle dulu. Pertanyaan utama pada flowchart sesi ini cuma satu: apakah TextBox kosong? Dari satu pertanyaan itu, aplikasi bisa memilih dua jalur yang berbeda.

Kalau jawabannya ya, aplikasi tidak boleh lanjut seperti biasa. Ia harus memberi tahu user bahwa input belum ada. Kalau jawabannya tidak, artinya data sudah tersedia dan aplikasi boleh masuk ke jalur normal.

Contoh membaca flowchart

  • User menekan tombol Hitung.
  • Aplikasi mengecek isi txtInput.Text.
  • Jika hasil cek = kosong, tampilkan pesan peringatan.
  • Jika hasil cek = terisi, tampilkan isi input sebagai hasil.

Flowchart itu penting karena saat nanti kalian melihat blok if then else, kalian tidak cuma meniru bentuknya. Kalian tahu bahwa blok itu sedang mewakili jalur ya/tidak yang tadi sudah dipahami dari flowchart.

Komponen Project

Mengatur Properties

Properties bukan inti logika, tetapi sangat membantu user saat memakai aplikasi. Pada project ini, properties yang paling terasa manfaatnya adalah bagian yang memberi petunjuk dan memperjelas output.

Contohnya, Hint TextBox bisa diisi supaya user tahu ia harus mengetik angka. Label hasil juga bisa diberi tampilan yang lebih menonjol, terutama ketika ingin menampilkan pesan error seperti “TextBox tidak boleh kosong!”.

Properties yang sebaiknya diperhatikan

  • Text / Hint pada TextBox: membantu user tahu apa yang harus diisi.
  • Text pada Button: gunakan kata yang jelas seperti “Hitung”.
  • Text pada Label hasil: boleh kosong di awal, lalu berubah saat tombol ditekan.
  • Font dan warna: usahakan pesan penting tetap mudah dibaca.

Namun ingat urutannya: rapikan secukupnya, lalu fokus ke blok validasi. Jangan sampai tampilan sudah cantik, tetapi jalur if - else-nya belum bekerja.

Dari Logika ke Blocks

Pseudocode adalah versi “bahasa manusia” dari program. Ia membantu kalian memahami isi program tanpa harus langsung berhadapan dengan bentuk blok puzzle yang kadang terlihat ramai.

Pada slide kiri, pseudocode menunjukkan bahwa event dimulai saat tombol diklik, lalu aplikasi mengecek kondisi TextBox. Setelah itu, program memilih salah satu dari dua jalur: jalur peringatan atau jalur normal.

Makna pseudocode sesi ini

  1. Ketika btnhitung.Click terjadi, program mulai berjalan.
  2. Program mengecek apakah txtInput.Text sama dengan teks kosong.
  3. Jika kosong, program mengubah lblHasil.Text menjadi pesan error.
  4. Jika tidak kosong, program mengubah lblHasil.Text menjadi isi input.

Dengan memahami pseudocode lebih dulu, kalian akan lebih mudah menempelkan screenshot Blocks nanti dan membaca bahwa setiap blok punya fungsi yang jelas.

Event btnhitung.Click

Semua aksi pada project ini diawali oleh event when btnhitung.Click. Artinya, aplikasi menunggu user menekan tombol Hitung. Sebelum itu, tidak ada proses validasi yang berjalan.

Ini penting karena pada aplikasi berbasis event seperti MIT App Inventor, program tidak berjalan dari atas ke bawah seperti teks biasa. Ia berjalan ketika ada pemicu, misalnya tombol ditekan.

Hal yang sering terlewat

  • Blok if then else harus diletakkan di dalam event.
  • Jika event salah, tombol terlihat ada, tetapi perilaku aplikasi tidak sesuai.
  • Kalau saat diklik tidak terjadi apa-apa, cek event dulu sebelum bagian lain.

Jadi, saat melihat screenshot Blocks, biasakan mencari blok paling luar lebih dulu. Pada sesi ini, blok paling luar itu adalah btnhitung.Click.

Membaca Kondisi If

Bagian kondisi adalah jantung validasi pada sesi ini. Di sinilah aplikasi bertanya: apakah isi TextBox kosong?

Secara teknis, project sample membandingkan txtInput.Text dengan teks kosong "". Kalau keduanya sama, berarti user belum mengisi apa pun. Kalau tidak sama, berarti input sudah ada.

Contoh kondisi

  • txtInput.Text = "" → kondisi benar → masuk jalur then.
  • txtInput.Text = "0" → kondisi salah → masuk jalur else.
  • txtInput.Text = "25" → kondisi salah → masuk jalur else.

Bagian ini sering membingungkan siswa karena angka 0 terlihat “kecil”, tapi sebenarnya tetap dianggap ada isi. Yang benar-benar kosong hanyalah saat user tidak mengetik apa pun.

Bagian Then

Bagian then adalah respons aplikasi ketika kondisi if bernilai benar. Pada project ini, itu berarti TextBox memang kosong.

Karena data belum ada, aplikasi tidak boleh pura-pura memproses. Sebaliknya, aplikasi harus memberi tahu user dengan jelas apa masalahnya.

Apa yang dilakukan bagian then?

  • Menghentikan jalur normal.
  • Mengarahkan output ke lblHasil.
  • Menampilkan pesan seperti “TextBox tidak boleh kosong!”.

Pesan seperti ini penting karena user jadi tahu langkah berikutnya: isi dulu TextBox, lalu tekan tombol lagi. Inilah contoh kecil bagaimana aplikasi membantu user, bukan malah membingungkan user.

Bagian Else

Bagian else berjalan ketika kondisi if bernilai salah. Dalam konteks project ini, itu berarti TextBox sudah terisi dan aplikasi boleh melanjutkan proses normal.

Project sample sengaja dibuat sederhana. Jadi pada jalur else, aplikasi hanya menampilkan kembali isi txtInput.Text ke lblHasil. Ini cukup untuk menunjukkan bahwa validasi berhasil membedakan dua kondisi.

Kenapa hasilnya cuma menampilkan input?

Karena fokus Sesi 9 bukan menghitung rumus baru, melainkan memastikan jalur validasi bekerja. Di sesi lain, bagian else bisa berisi perhitungan, konversi, atau proses yang lebih panjang.

Dengan desain seperti ini, kalian bisa sangat jelas melihat perbedaannya: kosong memberi pesan, terisi memberi output normal.

Membaca Rangkaian Lengkap

Pada slide kiri, rangkaian lengkap menunjukkan semua potongan logika digabung menjadi satu program. Ini membantu kalian melihat bagaimana event, kondisi, dan output saling terhubung.

Urutannya tetap perlu dibaca dari luar ke dalam. Mulai dari event tombol, lalu pindah ke kondisi if, lalu lihat cabang then dan else.

Cara membaca dari awal sampai akhir

  1. User menekan btnhitung.
  2. Aplikasi memeriksa txtInput.Text.
  3. Jika kosong, lblHasil diisi pesan error.
  4. Jika tidak kosong, lblHasil diisi nilai input.

Kalau nanti ada screenshot Blocks lengkap di kiri, gunakan empat langkah ini sebagai panduan supaya kalian tidak bingung melihat bentuk blok yang bertumpuk.

Membaca Tanpa Menjalankan

Reading Blocks adalah kemampuan memprediksi apa yang akan dilakukan program sebelum diuji. Ini sangat berguna saat kalian ingin mengecek logika tanpa harus selalu menekan tombol satu per satu.

Pada sesi ini, kuncinya sederhana: cek dulu isi TextBox. Kalau kosong, pikirkan jalur then. Kalau terisi, pikirkan jalur else.

Coba bayangkan

  • Jika TextBox kosong, output yang seharusnya muncul adalah pesan peringatan.
  • Jika TextBox berisi 0, output yang seharusnya muncul adalah 0.
  • Jika TextBox berisi 25, output yang seharusnya muncul adalah 25.

Kalau hasil asli saat testing berbeda dari prediksi ini, berarti ada bagian blok yang perlu diperiksa lagi. Jadi reading Blocks itu seperti membuat tebakan yang masuk akal sebelum pengujian.

Testing Dua Kondisi

Testing pada sesi ini minimal harus mencoba dua kondisi utama: input kosong dan input terisi. Kalau hanya mengetes satu kondisi saja, kalian belum tahu apakah validasinya benar-benar bekerja.

Tambahkan juga satu contoh angka 0. Ini penting karena banyak aplikasi pemula salah menganggap 0 sebagai kondisi kosong, padahal sebenarnya 0 adalah input yang sah.

Expected output yang perlu diingat

  • Kosong → tampil pesan “TextBox tidak boleh kosong!”.
  • 0 → tampil 0 sebagai output normal.
  • 25 → tampil 25 sebagai output normal.

Saat testing, jangan cuma melihat “jalan atau tidak”. Cocokkan juga apakah hasilnya sesuai dengan yang seharusnya. Itulah fungsi test case.

Debugging Terarah

Debugging akan terasa lebih gampang kalau kalian memulai dari gejalanya. Misalnya, output tidak berubah, atau angka 0 malah dianggap kosong. Dari gejala itu, kalian bisa menebak bagian mana yang perlu dicek dulu.

Jangan langsung menghapus semua blok. Kebiasaan itu malah membuat kalian kehilangan jejak masalahnya. Lebih baik periksa satu per satu.

Urutan cek yang aman

  1. Apakah event tombol sudah benar?
  2. Apakah kondisi membandingkan txtInput.Text dengan teks kosong?
  3. Apakah pesan peringatan diletakkan di bagian then?
  4. Apakah jalur normal diletakkan di bagian else?
  5. Apakah output diarahkan ke lblHasil?

Sesudah mengubah satu hal, test lagi dengan kasus yang sama. Cara ini membuat kalian tahu perubahan mana yang benar-benar memperbaiki bug.

Data Aman untuk Testing

Project Detektif Crash tidak membutuhkan data sungguhan. Untuk menguji aplikasi, kalian cukup memakai input latihan seperti kosong, 0, 7, atau 25.

Kebiasaan baik saat testing

  • Pakai data dummy.
  • Hindari data pribadi.
  • Kalau membuat screenshot, pastikan tidak ada info sensitif di layar.
  • Simpan project di akun sendiri.

Kebiasaan kecil seperti ini penting dibangun sejak sekarang, karena nanti kalian akan membuat aplikasi yang inputnya lebih banyak dan lebih sensitif.

Yang Sudah Dipelajari

Di Sesi 9, kalian belajar bahwa aplikasi yang baik tidak selalu langsung memproses input. Kadang tugas terpentingnya justru mengecek dulu apakah data dari user sudah siap.

Melalui project Detektif Crash, kalian berlatih membuat validasi sederhana agar aplikasi tidak langsung bermasalah saat TextBox kosong. Kalian juga belajar bahwa input kosong berbeda dari angka 0, dan bahwa if - else adalah alat yang tepat untuk menangani dua kondisi itu.

Inti sesi ini

  • Runtime error bisa muncul saat aplikasi berjalan.
  • Validasi input membantu mencegah error sederhana.
  • txtInput.Text dibandingkan dengan teks kosong.
  • Then dipakai untuk jalur peringatan.
  • Else dipakai untuk jalur normal.
  • lblHasil menampilkan pesan atau hasil.
  • Testing harus mencoba kondisi kosong, 0, dan input lain.

Pola berpikir ini akan terus dipakai di project App Inventor berikutnya. Semakin banyak input dari user, semakin penting juga kebiasaan mengecek data sebelum diproses.
