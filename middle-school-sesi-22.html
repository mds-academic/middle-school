Kenapa sesi ini penting?

Aplikasi bisa terlihat berhasil saat input normal, tetapi bermasalah saat input kosong, angka 0, atau tombol ditekan berkali-kali. Developer perlu menguji banyak kondisi agar aplikasinya lebih stabil.

Sesi ini mengajak kamu berpikir seperti tester sekaligus developer.

Kenapa stress test cukup panjang?

Testing yang baik tidak hanya mencoba kondisi mudah. Kita juga mencoba kondisi yang sering dilupakan, seperti input kosong, angka 0, nilai sama, dan tombol berulang.

Yang perlu kamu ingat

Di Sesi 21, bagian utama Budget Checker sudah bekerja: user memasukkan saldo dan harga, aplikasi membandingkan keduanya, lalu menampilkan hasil.

Kalau saldo cukup, aplikasi memberi feedback bahwa uangnya cukup. Kalau saldo kurang, aplikasi menghitung kekurangannya dengan hargaTarget - saldo.

Sekarang kita akan menguji kondisi yang sering terlewat, misalnya saat salah satu input masih kosong. Tujuannya bukan mengubah core mechanic, tetapi membuat aplikasi lebih aman dan lebih jelas saat digunakan.

Berpikir seperti tester

Tester tidak hanya mencari cara agar aplikasi berhasil. Tester juga mencoba kondisi yang mungkin membuat aplikasi bingung.

Dengan begitu, developer dapat menemukan masalah sebelum pengguna asli menemukannya.

Istilah testing

Memakai istilah yang tepat membantu developer berkomunikasi dengan jelas. Jika kamu hanya berkata “error”, orang lain belum tentu tahu apa yang terjadi.

Tuliskan hasil nyata agar bug mudah ditelusuri.

Expected dan Actual tidak boleh tertukar

Expected adalah hasil yang kamu harapkan berdasarkan aturan aplikasi. Actual adalah hasil yang benar-benar kamu lihat saat menjalankan aplikasi.

Status Pass berarti expected dan actual sama. Fail berarti berbeda.

Status membantu prioritas

Jika test Fail, developer tahu bagian itu perlu diperiksa. Jika Pass, bagian tersebut sudah sesuai pada test itu.

Namun, satu Pass tidak berarti seluruh aplikasi bebas bug. Tetap uji kondisi lain.

Stress test itu mencoba batas

Stress test membantu menemukan bug yang tidak muncul pada kondisi normal. Misalnya, aplikasi bisa benar pada 100000/75000, tetapi bermasalah saat saldo kosong.

Validasi sebelum hitung

Core mechanic hanya boleh berjalan jika input yang dibutuhkan sudah ada. Jika belum ada, aplikasi harus memberi pesan peringatan agar user tahu apa yang perlu diperbaiki.

Jangan samakan 0 dan blank

Dalam Budget Checker, saldo 0 bisa berarti user memang belum punya saldo. Itu berbeda dari user yang belum mengisi apa pun.

Validasi yang baik harus bisa membedakan dua kondisi ini.

Notifier bukan tombol

Notifier tidak terlihat seperti Button atau Label di layar aplikasi. Biasanya muncul di area non-visible components.

Di Blocks, kamu memanggil Notifier.ShowAlert untuk menampilkan pesan.

Kenapa core mechanic ada di ELSE terakhir?

Validasi bekerja seperti gerbang. Aplikasi mengecek beberapa kemungkinan error terlebih dahulu: dua input kosong, saldo kosong, atau harga kosong. Jika salah satu terjadi, aplikasi cukup menampilkan pesan peringatan.

ELSE terakhir artinya semua kondisi error di atas tidak terjadi. Di situlah core mechanic boleh berjalan.

Notifier saja belum cukup

Menampilkan pesan peringatan belum tentu menghentikan alur program. Kamu perlu menempatkan core mechanic pada jalur yang benar, yaitu setelah input lolos validasi.

Mulai dari komponen

Sebelum memakai Notifier di Blocks, pastikan komponen Notifier sudah ditambahkan di Designer. Karena Notifier adalah komponen non-visible, kamu tidak akan melihatnya di layar aplikasi, tetapi bloknya akan muncul di area Blocks.

Variable saldo dan hargaTarget tetap digunakan. Bedanya, sekarang kita mengecek input lebih dulu sebelum nilai diproses lebih jauh.

Kenapa cek dua kosong dulu?

Jika saldo dan harga sama-sama kosong, pesan yang paling membantu adalah pesan yang menyebut dua input. User jadi tahu bahwa dua bagian itu perlu diisi, bukan hanya salah satunya.

Setelah Notifier muncul, perhitungan belum boleh berjalan. Data yang dibutuhkan belum lengkap.

Pesan yang spesifik membantu user

Pesan “Input salah” terlalu umum. Pesan “Saldo belum diisi” lebih membantu karena user tahu bagian mana yang perlu diperbaiki.

Validasi satu per satu

Dengan mengecek saldo kosong dan harga kosong secara terpisah, aplikasi dapat memberi pesan yang lebih tepat. Ini membuat UX lebih jelas.

Jalur valid

ELSE terakhir berarti semua kondisi error di atas tidak terjadi. Dengan kata lain, saldo dan harga sudah terisi dan bisa dipakai untuk perhitungan.

Core mechanic dari Sesi 21 tidak dihapus. Kita hanya menempatkannya di jalur yang lebih aman.

Coba beberapa kondisi

Gunakan simulator ini seperti test case kecil. Coba keduanya kosong, satu kosong, saldo 0, saldo sama dengan harga, saldo cukup, dan saldo kurang.

Perhatikan kapan Notifier seharusnya muncul dan kapan core mechanic seharusnya berjalan.

Tulis bukti, bukan tebakan

Actual Result harus ditulis dari hasil yang kamu lihat saat menjalankan aplikasi. Kalau aplikasi menunjukkan hasil yang salah, tulis hasil salah itu dengan jelas.

Perbaikan butuh bukti

Developer tidak cukup berkata “sudah diperbaiki”. Harus ada test yang menunjukkan hasilnya sekarang sesuai expected result.

Kenapa fitur lama perlu dicek?

Kadang saat memperbaiki satu bug, kita tidak sengaja merusak bagian lain. Regression check memastikan fitur yang sebelumnya benar tetap benar.

Pesan tidak otomatis menghentikan program

Notifier hanya menampilkan pesan. Kalau blok perhitungan tetap berada setelah Notifier di jalur yang sama, aplikasi masih bisa menghitung.

Karena itu, struktur if/else sangat penting.

Cara mengecek bug ini

Masukkan saldo 0 dan harga 75000. Aplikasi seharusnya menghitung kekurangan, bukan menganggap saldo belum diisi.

User bisa melakukan hal yang tidak kita duga

Pengguna mungkin klik tombol berkali-kali, pindah screen, lalu kembali lagi. Testing membantu memastikan aplikasi tetap stabil pada pola penggunaan seperti itu.

Kalau navigasi tidak bekerja, cek nama screen dan event tombolnya. Kalau aplikasi terasa tidak stabil setelah tombol ditekan berulang, ulangi test case dan catat actual result dengan jelas.

Testing tetap harus aman

Karena project membahas budget, tetap gunakan angka simulasi. Tujuan kita mengecek logic, bukan data asli siapa pun.

Reset sebagai latihan tambahan

Reset membantu user memulai input baru. Namun, ini bukan target utama Sesi 22. Target utama tetap validasi input dan re-test.

Yang perlu diingat

Aplikasi yang bagus tidak hanya bekerja saat input normal. Aplikasi juga perlu memberi respons yang jelas saat user belum mengisi data dengan benar.

Testing, fixing, dan re-testing adalah kebiasaan developer yang penting.
