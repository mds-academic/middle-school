Gambaran Sesi 15

Di sesi ini kalian belajar membuat aplikasi yang tidak hanya berada di satu layar. Banyak aplikasi asli punya beberapa halaman, misalnya halaman awal, katalog, detail barang, keranjang, dan profil.

Project hari ini dibuat sederhana dulu: Screen1 sebagai halaman awal atau beranda, lalu Screen2 sebagai katalog toko online. Fokus utama kita adalah memahami alur pindah layar, bukan membuat toko online yang terlalu kompleks.

  • Kalian akan membaca user flow: Screen1 → Screen2 → Screen1.
  • Kalian akan memakai event Button.Click dan block open another screen.
  • Kalian juga akan menguji apakah tombol membuka layar tujuan yang benar.

Tujuan Belajar

Tujuan sesi ini adalah membuat kalian paham bahwa setiap layar punya tugas. Screen tidak hanya sekadar “halaman tambahan”, tetapi bagian dari alur aplikasi yang membantu user bergerak dari satu tujuan ke tujuan lain.

Dalam project toko online, user mulai dari halaman awal. Setelah menekan tombol masuk, user diarahkan ke katalog. Dari katalog, user harus bisa kembali ke halaman awal. Alur ini disebut navigasi dua arah.

  • Memahami fungsi Screen1 dan Screen2.
  • Membaca user flow dengan panah dan nama tombol.
  • Menggunakan open another screen dengan nama Screen tujuan yang tepat.
  • Melakukan debugging jika tombol diam atau membuka layar yang salah.

Persiapan Sebelum Praktik

Project multi-screen lebih mudah dibuat kalau kalian mengecek layar satu per satu. Jangan langsung membuat semua blok sekaligus. Mulai dari memastikan Screen1 siap, lalu pindah ke Screen2, baru masuk ke Blocks.

Karena temanya toko online, ingat bahwa project ini hanya simulasi. Kita tidak membuat sistem belanja sungguhan, tidak meminta data pembayaran, dan tidak membutuhkan data pribadi.

  • Screen1 dipakai sebagai halaman awal.
  • Screen2 dipakai sebagai katalog.
  • AI2 Companion dipakai untuk melihat apakah perpindahan layar sudah berjalan.

Mengikuti Alur Sesi

Mulai dari LMS dulu agar kalian tahu target project dan urutan belajarnya. Setelah itu, kalian bisa berpindah ke MIT App Inventor untuk membuat aplikasi.

Kalau membuka sesi yang salah, materi dan project bisa tidak sesuai. Jadi cek lagi judulnya: Lesson 15: Toko Online – Multi-Screen dan Navigasi Aplikasi.

  • Buka materi utama sebelum coding.
  • Gunakan sample project atau starter sesuai instruksi guru.

Alasan Memakai Multi-Screen

Aplikasi yang rapi biasanya membagi informasi ke beberapa layar. Halaman awal bisa dipakai untuk menyapa user atau memberi tombol masuk. Katalog bisa dipakai untuk menampilkan barang. Detail produk bisa dibuat di layar lain jika aplikasinya dikembangkan.

Dengan multi-screen, user tidak perlu melihat semua informasi sekaligus. Mereka bergerak mengikuti alur yang sudah dirancang.

  • Layar menjadi lebih rapi dan tidak penuh.
  • Setiap Screen punya tujuan yang lebih mudah dipahami.
  • Navigasi membantu user pindah dari satu bagian aplikasi ke bagian lain.

Perbedaan yang Sering Tertukar

Screen adalah halaman. Komponen adalah benda yang dipasang di halaman itu. Jadi Button bukan Screen, dan Screen bukan Button.

Di MIT App Inventor, setiap Screen punya area Designer dan Blocks sendiri. Ini penting, karena event tombol sebaiknya dibuat di Screen tempat tombol itu berada.

  • Screen1 berisi komponen untuk halaman awal.
  • Screen2 berisi komponen untuk katalog.
  • btnMasuk adalah tombol di Screen1.
  • btnKembali adalah tombol di Screen2.

Membaca User Flow

User flow membantu kalian melihat arah perpindahan layar sebelum menulis Blocks. Ini seperti peta jalan: tombol mana yang ditekan, lalu layar mana yang terbuka.

Untuk project minimum, alurnya hanya dua layar. Tetapi pola yang sama bisa dipakai untuk aplikasi yang lebih besar, misalnya menambah Screen3 untuk detail barang.

  • btnMasuk menjadi panah dari Screen1 ke Screen2.
  • btnKembali menjadi panah dari Screen2 ke Screen1.
  • Setiap panah dalam user flow harus punya event Button.Click di Blocks.

Merancang Sebelum Coding

Sebelum membangun aplikasi, biasakan merancang alur dulu. Ini membuat kalian tahu tombol apa yang perlu dibuat dan Screen mana yang menjadi tujuannya.

Kesalahan navigasi sering terjadi karena siswa langsung coding tanpa menentukan alur. Akibatnya, tombol bisa membuka layar yang salah atau hanya bisa pergi tanpa bisa kembali.

  • Tentukan layar awal.
  • Tentukan tombol untuk pindah layar.
  • Tentukan layar tujuan.
  • Pastikan ada tombol kembali jika user perlu kembali ke halaman sebelumnya.

Melihat Bentuk Aplikasi

Preview ini membantu kalian membayangkan hasil akhir sebelum membuatnya di MIT App Inventor. Screen1 tidak perlu penuh dengan produk. Screen1 cukup menjadi pintu masuk ke katalog.

Screen2 berisi katalog produk. Di akhir halaman katalog, ada tombol kembali supaya user tidak terjebak di layar itu.

  • Screen1 = halaman awal atau beranda.
  • Screen2 = katalog produk.
  • Tombol Masuk dan Kembali adalah bagian penting dari navigasi.

Designer Screen1

Di Screen1, komponen dibuat sederhana. Tujuannya bukan menampilkan semua barang, tetapi memberi halaman awal yang jelas dan tombol untuk menuju katalog.

Nama tombol perlu rapi karena nanti dipanggil di Blocks. Gunakan nama seperti btnMasuk, bukan Button1, agar mudah dibaca saat debugging.

  • lblJudul: judul aplikasi.
  • lblDeskripsi: kalimat pendek untuk user.
  • btnMasuk: tombol yang membuka Screen2.

Designer Screen2

Screen2 berisi katalog. Tampilannya bisa berbeda dari Screen1 karena tugasnya berbeda. Kalau Screen1 adalah pintu masuk, Screen2 adalah tempat user melihat produk.

Tombol kembali perlu dibuat di Screen2 agar user bisa kembali ke halaman awal. Tanpa tombol kembali, user flow menjadi satu arah dan kurang nyaman dipakai.

  • lblKatalog: judul halaman katalog.
  • imgBarang: gambar atau ilustrasi produk.
  • btnKembali: tombol yang membuka Screen1.

Kenapa Naming Penting?

Di App Inventor, project kecil mungkin masih bisa dibaca walau tombol bernama Button1. Tetapi saat project mulai punya beberapa Screen, nama yang jelas membuat pekerjaan jauh lebih mudah.

Misalnya, btnMasuk langsung memberi tahu bahwa tombol itu dipakai untuk masuk ke halaman berikutnya. btnKembali memberi tahu bahwa tombol itu dipakai untuk kembali.

  • Gunakan awalan btn untuk Button.
  • Gunakan nama yang menjelaskan fungsi tombol.
  • Hindari nama yang membingungkan seperti Button1, Button2, Button3 jika sudah banyak komponen.

Mengatur Tampilan agar User Paham

Properties membantu user memahami fungsi layar dan tombol. Teks tombol sebaiknya singkat, tetapi jelas. Misalnya MASUK untuk membuka katalog, KEMBALI untuk kembali ke halaman awal.

Selain tombol, judul Screen juga membantu kalian saat berpindah antar Screen di App Inventor. Saat membuka tab Screen2, pastikan kalian benar-benar sedang mengedit Screen2, bukan masih di Screen1.

  • Periksa teks tombol di Designer.
  • Periksa nama komponen di panel Components.
  • Periksa Screen yang sedang aktif sebelum membuka Blocks.

Membaca Blok Navigasi

Blok navigasi tidak bekerja sendiri. Pertama, harus ada event yang menjadi pemicu, yaitu tombol diklik. Kedua, harus ada perintah untuk membuka layar lain. Ketiga, harus ada nama Screen tujuan.

Bagian screenName harus tepat. Kalau seharusnya membuka Screen2 tetapi tertulis Screen1, maka tombol akan membuka layar yang salah.

  • Button.Click menjawab “kapan perintah dijalankan?”
  • open another screen menjawab “apa yang dilakukan?”
  • screenName menjawab “layar mana yang dibuka?”

Memahami Tombol Masuk

Tombol Masuk berada di Screen1. Saat tombol ini ditekan, aplikasi harus membuka Screen2. Jadi Blocks untuk tombol ini dibuat pada Screen1, bukan Screen2.

Kalau tombol Masuk tidak melakukan apa-apa, cek apakah event btnMasuk.Click sudah dibuat dan apakah block open another screen sudah dimasukkan ke dalam event tersebut.

  • Lokasi tombol: Screen1.
  • Event yang dipakai: btnMasuk.Click.
  • Screen tujuan: Screen2.

Event untuk Tombol Masuk

Ini adalah bagian awal kode navigasi dari Screen1 ke Screen2. Blok when btnMasuk.Click do artinya: saat user menekan tombol Masuk, jalankan perintah yang ada di dalamnya.

Pada gambar ini, bagian dalam event masih kosong. Tugas berikutnya adalah memasukkan block open another screen ke dalam area do.

  • Jangan meletakkan block navigasi di luar event.
  • Pastikan event yang dipilih adalah milik btnMasuk.
  • Event ini dibuat di Blocks milik Screen1.

Perintah Membuka Screen2

Block open another screen membutuhkan nama Screen tujuan. Pada tombol Masuk, nama tujuan yang benar adalah Screen2.

Perhatikan huruf dan angka pada nama Screen. Nama Screen2 harus sesuai dengan nama Screen yang ada di project. Jika Screen2 belum dibuat, navigasi bisa gagal.

  • Gunakan Screen2 untuk pergi ke katalog.
  • Pastikan Screen2 memang sudah ada di project.
  • Masukkan block ini ke dalam event btnMasuk.Click.

Membaca Kode btnMasuk

Kode lengkap ini menggabungkan event dan perintah navigasi. Saat tombol btnMasuk diklik, aplikasi menjalankan block open another screen dengan tujuan Screen2.

Ini adalah contoh hubungan antara user flow dan Blocks. Panah Screen1 → Screen2 di flowchart diwakili oleh satu event tombol ini.

  • Kalau tombol Masuk diam, cek apakah block berada di dalam event.
  • Kalau membuka layar salah, cek isi screenName.
  • Kalau Screen2 tidak terbuka, cek apakah Screen2 sudah dibuat.

Memahami Tombol Kembali

Tombol Kembali berada di Screen2. Artinya, Blocks untuk tombol ini dibuat saat kalian sedang membuka Screen2. Jangan membuat semua event di Screen1, karena tombol yang ada di Screen2 harus diatur dari Screen2.

Tujuannya adalah membuka Screen1 kembali. Dengan begitu, aplikasi punya navigasi dua arah dan user tidak terjebak di katalog.

  • Lokasi tombol: Screen2.
  • Event yang dipakai: btnKembali.Click.
  • Screen tujuan: Screen1.

Event untuk Tombol Kembali

Blok when btnKembali.Click do artinya: saat tombol Kembali ditekan, jalankan perintah di dalamnya.

Bagian kosong pada event ini harus diisi dengan perintah untuk membuka Screen1. Kalau dibiarkan kosong, tombol Kembali tidak akan melakukan apa-apa saat dites.

  • Pastikan memilih event milik btnKembali.
  • Buat event ini saat sedang berada di Screen2.
  • Isi ruang do dengan block navigasi.

Perintah Membuka Screen1

Untuk tombol Kembali, Screen tujuan yang benar adalah Screen1. Ini kebalikan dari tombol Masuk.

Kalau nama Screen tertukar, tombol Kembali bisa membuka layar yang sama atau tidak membawa user ke halaman awal. Karena itu, selalu cocokkan tombol dengan arah panah pada user flow.

  • btnMasuk → Screen2.
  • btnKembali → Screen1.
  • Jangan tertukar antara Screen1 dan Screen2.

Membaca Kode btnKembali

Kode ini mewakili panah balik dari Screen2 ke Screen1. Saat tombol btnKembali diklik, aplikasi membuka Screen1.

Dengan kode ini dan kode btnMasuk sebelumnya, aplikasi sudah punya navigasi dua arah. User bisa masuk ke katalog dan kembali ke halaman awal.

  • Kode ini dibuat pada Screen2.
  • Perintahnya membuka Screen1.
  • Testing perlu dilakukan bolak-balik, bukan hanya sekali.

Review Kode Final

Kode final navigasi terdiri dari dua event. Event pertama ada di Screen1 dan membuka Screen2. Event kedua ada di Screen2 dan membuka Screen1.

Jika kalian bisa menjelaskan dua event ini dengan bahasa sendiri, berarti kalian sudah memahami inti multi-screen. Bentuk aplikasinya boleh berbeda, tetapi logika navigasinya tetap sama.

  • Screen1: btnMasuk.Click → open another screen Screen2.
  • Screen2: btnKembali.Click → open another screen Screen1.
  • Setiap arah navigasi harus dites langsung.

Memahami Perilaku Aplikasi

Simulator ini meniru logika project. Saat berada di Screen1, tombol Masuk membuka Screen2. Saat berada di Screen2, tombol Kembali membuka Screen1.

Perhatikan bahwa tombol tidak otomatis berpindah layar hanya karena ada di tampilan. Tombol baru bekerja karena ada event Button.Click dan perintah open another screen di Blocks.

  • Tampilan tombol dibuat di Designer.
  • Perilaku tombol dibuat di Blocks.
  • Testing memastikan tampilan dan perilaku sudah cocok.

Expected Output untuk Navigasi

Sebelum menjalankan aplikasi, tentukan dulu hasil yang diharapkan. Ini disebut expected output. Setelah dites, hasil sebenarnya disebut actual output.

Kalau expected dan actual berbeda, berarti ada bug. Misalnya, tombol Masuk seharusnya membuka Screen2, tetapi malah tetap di Screen1. Itu berarti bagian event, perintah, atau screenName perlu dicek.

  • Test case 1: btnMasuk harus membuka Screen2.
  • Test case 2: btnKembali harus membuka Screen1.
  • Test case 3: ulangi flow untuk memastikan navigasi stabil.

Debugging Berdasarkan Gejala

Debugging akan lebih mudah kalau kalian mulai dari gejalanya. Jangan langsung menghapus semua blok. Cari dulu: tombol diam, layar salah, atau kode dibuat di Screen yang tidak tepat.

Project multi-screen punya bug khas: nama Screen tertukar, event tombol dibuat di Screen yang salah, atau Screen tujuan belum ada.

  • Tombol diam → cek event dan posisi block.
  • Layar salah → cek screenName.
  • Tombol di Screen2 tidak bekerja → cek apakah kalian sedang mengedit Blocks Screen2.

Testing Dua Arah

Jangan hanya mengetes tombol Masuk. Project baru benar-benar stabil jika tombol Kembali juga bekerja. Setelah itu, ulangi alurnya sekali lagi untuk memastikan navigasi tidak hanya berhasil satu kali.

Testing seperti ini melatih kalian membandingkan expected output dan actual output. Jika berbeda, gunakan checklist debugging pada slide sebelumnya.

  • Test Screen1 → Screen2.
  • Test Screen2 → Screen1.
  • Ulangi untuk memastikan tidak ada tombol yang salah arah.

Dari Rencana ke Aplikasi

Flowchart adalah rencana. Blocks adalah instruksi yang benar-benar dijalankan aplikasi. Keduanya harus cocok.

Kalau flowchart menunjukkan tombol Masuk ke Screen2, maka di Blocks harus ada event btnMasuk.Click yang membuka Screen2. Kalau flowchart menunjukkan tombol Kembali ke Screen1, maka di Blocks harus ada event btnKembali.Click yang membuka Screen1.

  • Satu panah navigasi = satu event tombol.
  • Label panah = tombol yang ditekan.
  • Akhir panah = Screen yang harus ditulis pada screenName.

Keamanan Digital dalam Simulasi

Walaupun project ini bertema toko online, kalian tidak sedang membuat sistem belanja asli. Karena itu, tidak ada alasan untuk memasukkan data pribadi atau data pembayaran sungguhan.

Gunakan data dummy agar project tetap aman. Contoh: nama toko fiktif, daftar produk latihan, harga simulasi, dan gambar yang aman digunakan untuk belajar.

  • Jangan memasukkan password atau akun asli.
  • Jangan memasukkan nomor pembayaran asli.
  • Jangan meminta user mengisi data sensitif pada project latihan.

Mengembangkan Navigasi

Setelah dua Screen berhasil, kalian bisa membayangkan versi yang lebih lengkap. Misalnya, Screen3 berisi detail barang. Tombol Detail di katalog membuka Screen3, lalu tombol Kembali di Screen3 membuka Screen2.

Prinsipnya tetap sama: setiap tombol butuh event Button.Click dan perintah open another screen ke tujuan yang benar.

  • btnDetail → Screen3.
  • btnKembaliDetail → Screen2.
  • Test lagi setiap arah navigasi yang baru dibuat.

Menutup Praktik

Sebelum project dikumpulkan, pastikan perubahan terakhir sudah tersimpan dan dites. Project yang terlihat bagus belum tentu navigasinya benar, jadi testing tetap wajib.

Refleksi yang bagus biasanya menghubungkan flowchart dengan Blocks. Misalnya, “btnMasuk menuju Screen2 karena di user flow panahnya dari halaman awal ke katalog.”

  • Simpan project sebelum keluar dari App Inventor.
  • Tunjukkan dua Screen kepada guru jika diminta.
  • Jelaskan hubungan tombol, event, dan Screen tujuan.
