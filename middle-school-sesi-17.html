Misi hari ini

Buat rancangan aplikasi: masalah, target user, value proposition, fitur utama, user flow, wireframe, daftar komponen, konsep coding, dan outline pitch deck.

Kenapa Harus Merancang Dulu?

Developer tidak langsung menyusun Blocks tanpa tahu masalah dan alurnya.

Tanpa rancangan

Bingung mulai dari mana, fitur terlalu banyak, screen tidak jelas, dan mudah tersesat saat coding.

Dengan rancangan

Masalah jelas, fitur utama fokus, alur mudah diuji, dan coding punya arah.

Wireframe vs Desain Final

Wireframe

  • Masih sederhana.
  • Bisa hitam putih.
  • Fokus ke posisi dan fungsi.
  • Cepat direvisi.

Desain final

  • Warna sudah dipilih.
  • Gambar lebih rapi.
  • Detail visual lebih lengkap.
  • Biasanya dibuat setelah alur jelas.

Apa Itu User Flow?

User flow menunjukkan langkah user dari awal sampai tujuan selesai.

Buka app→Masukkan saldo→Masukkan harga→Tekan cek→Lihat hasil

User flow menjawab pertanyaan...

Value Proposition

Value proposition menjawab: “Kenapa orang perlu memakai aplikasi ini?”

Pola sederhana

Target user + masalah + solusi/fitur + manfaat

Contoh: Budget Checker membantu siswa memeriksa apakah saldo cukup untuk membeli barang melalui fitur perbandingan saldo dan harga, sehingga mereka bisa membuat keputusan belanja lebih terencana.

Apa Itu Pitch Deck?

Pitch deck adalah kumpulan slide singkat untuk menjelaskan ide aplikasi.

Bukan tempat menumpuk semua tulisan

Pitch deck sebaiknya singkat, jelas, dan mudah dipahami. Fokusnya: masalah → solusi → manfaat → cara kerja.

Tujuannya agar guru, teman, atau juri memahami kenapa ide aplikasi ini menarik dan bisa dibuat.

Outline Pitch Deck 3 Slide

Slide 1 — Masalah

Nama aplikasi, target user, dan masalah utama.

Slide 2 — Solusi

Solusi, value proposition, dan fitur utama.

Slide 3 — Cara Kerja

User flow, wireframe, atau gambaran kerja aplikasi.

Contoh: Budget Checker

Problem

Siswa ingin membeli barang, tetapi belum tahu uang jajannya cukup atau tidak.

Target User

Siswa SMP yang ingin mengatur uang jajan lebih bijak.

Solution

Aplikasi mengecek saldo, harga target, selisih uang, dan memberi pengingat needs/wants.

Cara Kerja

Masukkan saldo → masukkan harga → cek budget → lihat hasil.

Feedback Teman

Sebelum selesai, tukarkan rancangan dengan teman.

  • Apakah masalah aplikasi jelas?
  • Apakah target user jelas?
  • Apakah solusi sesuai masalah?
  • Apakah user flow mudah dipahami?
  • Apakah wireframe menunjukkan elemen penting?

Challenge: User Persona

👩‍🎓

Dita

Pengguna utama: siswa SMP yang mengatur uang saku.

Kebutuhan: tahu apakah uangnya cukup sebelum membeli barang.

Kesulitan: sering lupa menghitung sisa uang.

Tujuan: membuat keputusan belanja lebih terencana.

Persona harus fiktif. Jangan tulis alamat, nomor telepon, nama sekolah asli, atau data pribadi.

Gambaran Sesi 17

Sesi ini mengajak siswa berpindah dari membuat project contoh ke merancang project sendiri. Mereka belum perlu membuat aplikasi final, tetapi harus bisa menjelaskan masalah, solusi, dan cara kerja aplikasi.

Materi utamanya adalah wireframe, user flow, value proposition, pitch deck, pemetaan komponen MIT App Inventor, dan konsep coding yang akan dipakai.

Analogi Arsitek

Sama seperti arsitek membuat denah sebelum membangun rumah, developer membuat rancangan sebelum membangun aplikasi. Denah membantu menentukan bagian mana yang dibutuhkan dan bagaimana hubungan antarbagian.

Dalam konteks aplikasi, rancangan awal membantu siswa menentukan pengguna, masalah, fitur utama, screen, komponen, dan logika program.

Tujuan Belajar

Siswa belajar mengubah ide mentah menjadi rancangan yang bisa dikerjakan. Sebuah ide tidak cukup hanya “aplikasi keuangan” atau “aplikasi toko”. Ide perlu dipersempit menjadi masalah, target user, fitur, alur, dan tampilan awal.

Hasil sesi ini menjadi bekal untuk sesi-sesi berikutnya saat siswa mulai membangun project aplikasi.

Menggunakan Pengalaman Sebelumnya

Siswa sudah mengenal input, output, event, kondisi, ListPicker, Notifier, dan multi-screen. Sesi 17 mengajak mereka memilih konsep yang cocok untuk ide masing-masing.

Tekankan bahwa aplikasi sederhana dengan satu fitur utama yang berjalan baik lebih bagus daripada aplikasi besar yang tidak selesai.

Memahami Wireframe

Wireframe adalah denah tampilan aplikasi. Di dalamnya kita menentukan letak judul, input, tombol, hasil, gambar, atau navigasi. Wireframe belum perlu warna final atau desain yang lengkap.

Untuk siswa SMP, wireframe cukup berupa kotak, garis, label, dan panah. Fokusnya adalah menjawab: “Di layar ini user melihat apa dan melakukan apa?”

Miskonsepsi Umum

Banyak siswa merasa wireframe harus indah. Padahal wireframe dibuat agar ide cepat terlihat dan mudah diperbaiki. Jika sejak awal terlalu fokus pada warna, siswa bisa lupa fungsi aplikasi.

Tekankan bahwa wireframe adalah rancangan awal, bukan poster promosi.

Memahami User Flow

Kalau wireframe menjawab “seperti apa tampilan screen?”, user flow menjawab “apa urutan langkah pengguna?”. User flow biasanya memakai kotak dan panah.

User flow membantu siswa melihat apakah aplikasi masuk akal. Jika user harus melihat hasil sebelum memasukkan data, berarti alurnya perlu diperbaiki.

Membuat Manfaat Aplikasi Jelas

Value proposition bukan daftar fitur. Value proposition menjelaskan manfaat utama bagi pengguna. Jadi, bukan hanya “ada input saldo dan tombol cek”, tetapi “membantu siswa membuat keputusan belanja lebih terencana”.

Jika siswa kesulitan, minta mereka mengisi pola: aplikasi ini membantu siapa, mengatasi masalah apa, dengan fitur apa, supaya manfaatnya apa.

Tiga Hal Pertama

Masalah, target user, dan solusi harus nyambung. Jika masalahnya dialami siswa SMP, maka solusi dan fitur juga perlu sesuai untuk siswa SMP.

Contoh yang kurang tepat: masalahnya “siswa lupa menabung”, tetapi solusinya “aplikasi kalkulator diskon restoran”. Masalah dan solusi belum terhubung.

Memilih Masalah yang Cocok

Masalah yang dipilih sebaiknya dekat dengan kehidupan siswa dan tidak membutuhkan sistem yang terlalu rumit. Ide yang sederhana tetapi jelas lebih baik daripada ide besar yang tidak selesai.

Guru bisa mengarahkan siswa untuk memilih masalah yang bisa diselesaikan dengan satu fitur utama terlebih dahulu.

Validasi Ide Awal

Sebelum lanjut ke wireframe, siswa perlu mengecek apakah idenya realistis. Ide yang terlalu besar bisa membuat sesi berikutnya sulit berjalan.

Checklist ini membantu siswa menyaring ide agar tetap sesuai durasi project dan konsep coding yang sudah dipelajari.

Separuh Awal Rancangan

Langkah 1 sampai 6 berfokus pada isi ide. Siswa belum menggambar screen dulu, karena mereka perlu memahami masalah dan fitur yang akan dibuat.

Urutan ini mencegah siswa membuat tampilan keren untuk aplikasi yang masalahnya belum jelas.

Separuh Akhir Rancangan

Langkah 7 sampai 12 mengubah ide menjadi bentuk yang lebih teknis dan siap dipresentasikan. Di sini siswa mulai memikirkan screen, komponen, dan cara kerja aplikasi.

Hasil akhirnya adalah rancangan yang cukup jelas untuk dibawa ke proses pembuatan aplikasi berikutnya.

Memberi Nama Project

Nama aplikasi membantu orang lain memahami fungsi project. Nama tidak harus sempurna, tetapi jangan terlalu umum atau meniru brand terkenal.

Guru dapat meminta siswa menulis 2-3 alternatif nama, lalu memilih satu yang paling jelas.

Menjaga Scope Project

Prioritas fitur membantu siswa tidak membuat project terlalu besar. Semua ide tidak harus dimasukkan ke versi pertama.

Must Have adalah fitur yang membuat aplikasi bisa menjalankan tujuan utamanya. Nice to Have dan Future Idea bisa menunggu jika fitur utama sudah berhasil.

Screen Sesuai Kebutuhan

Banyak screen tidak selalu berarti aplikasi lebih baik. Setiap screen harus punya alasan. Jika satu screen sudah cukup, lebih baik mulai dari satu screen agar project selesai.

Jika aplikasi memang butuh halaman tambahan, siswa perlu menjelaskan hubungan antar screen lewat user flow.

Apa yang Harus Terlihat di Wireframe?

Wireframe harus cukup jelas untuk dibaca orang lain. Orang yang melihatnya perlu bisa menebak: user mengisi apa, menekan apa, dan melihat hasil di mana.

Untuk MIT App Inventor, wireframe juga membantu siswa membayangkan komponen apa yang diperlukan di Designer.

Dari Wireframe ke Designer

Pemetaan komponen membantu siswa mengubah gambar menjadi bagian nyata di MIT App Inventor. Setiap elemen di wireframe sebaiknya punya pasangan komponen.

Nama komponen yang jelas juga memudahkan saat nanti masuk ke Blocks. Misalnya btnCek lebih mudah dipahami daripada Button1.

Belum Perlu Blocks Lengkap

Pada sesi ini siswa tidak harus menulis Blocks lengkap. Yang penting, mereka bisa memperkirakan konsep coding apa yang akan dibutuhkan.

Contohnya, aplikasi Budget Checker kemungkinan membutuhkan input saldo, input harga, operator perbandingan, penghitungan selisih, dan if-then-else.

Memahami Pitch Deck

Pitch deck bukan laporan panjang. Pitch deck adalah alat bantu presentasi agar ide bisa diceritakan dengan runtut.

Dalam konteks kelas, pitch deck membantu siswa menjelaskan project sebelum atau sambil menunjukkan aplikasi yang dibuat.

Versi Sederhana Pitch Deck

Untuk tahap awal, tiga slide inti sudah cukup. Struktur ini memaksa siswa memilih informasi yang paling penting.

Jika nanti project berkembang, deck bisa ditambah. Tetapi pada sesi ini, tujuan utamanya adalah membuat outline yang jelas.

Membaca Sample Project

Contoh Budget Checker menunjukkan ide yang fokus: masalahnya jelas, target user jelas, fitur utama tidak terlalu banyak, dan cara kerja mudah dijelaskan.

Contoh ini bisa menjadi inspirasi, tetapi siswa tetap perlu membuat ide mereka sendiri. Jangan semua kelompok memakai nama dan masalah yang sama.

Peer Feedback untuk Rancangan

Feedback pada sesi ini bukan lagi hanya untuk aplikasi yang sudah jadi, tetapi untuk rancangan. Teman bisa membantu melihat apakah ide mudah dipahami dan realistis dibuat.

Feedback tetap perlu spesifik dan sopan. Misalnya: “User flow sudah jelas, tetapi wireframe belum menunjukkan tombol simpan.”

User Persona

User persona adalah gambaran pengguna fiktif yang mewakili target pengguna. Persona membantu siswa membayangkan kebutuhan dan kesulitan user dengan lebih nyata.

Persona tidak boleh berisi data pribadi asli. Gunakan nama dan informasi fiktif yang aman.

Bukti Belajar

Output minimum ini menjadi bukti bahwa siswa siap masuk ke tahap pembuatan aplikasi. Jika salah satu bagian kosong, kemungkinan siswa akan kesulitan pada sesi berikutnya.

Guru dapat meminta siswa menunjukkan rancangan, bukan hanya menjelaskan lisan.

Refleksi Akhir

Refleksi membantu siswa mengecek apakah ide mereka sudah cukup jelas. Jika mereka belum bisa menjawab tiga pertanyaan ini, rancangan perlu diperbaiki sebelum lanjut.

Jawaban refleksi juga bisa menjadi bahan pembuka pitch deck pada pertemuan berikutnya.

Penutup

Di sesi ini siswa menyiapkan fondasi project: apa masalahnya, siapa usernya, bagaimana solusi bekerja, dan seperti apa tampilan awalnya.

Rancangan ini akan membantu sesi berikutnya berjalan lebih lancar karena siswa tidak mulai coding dari halaman kosong.
