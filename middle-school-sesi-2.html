Kenapa UI Perlu Dirancang?

Coba bayangkan aplikasi yang tombolnya kecil, inputnya tidak jelas, dan hasilnya muncul di tempat yang sulit ditemukan.

Situasi: Kamu membuka aplikasi kalkulator. Ada kotak kosong, tombol “OK”, dan teks “hasil”, tetapi kamu tidak yakin harus mulai dari mana.

UI yang jelas membuat user tahu langkah pertama, tombol aksi, dan tempat melihat hasil.

Project yang Akan Kamu Buat

Kalkulator Saku UI adalah latihan membuat tampilan aplikasi sebelum aplikasi benar-benar menghitung. Fokusnya bukan rumus matematika dulu, tetapi cara menyusun layar agar pengguna tahu harus mengetik di mana, menekan tombol apa, dan melihat hasil di bagian mana.

Target minimum

Aplikasi memiliki judul, TextBox untuk input angka, tombol HITUNG, Label hasil, layout yang rapi, dan satu event sederhana saat tombol ditekan.

Di dunia nyata, aplikasi yang fiturnya bagus tetap bisa gagal dipakai kalau tampilannya membingungkan. Karena itu, sesi ini melatih cara berpikir sebagai developer: bukan hanya “apakah aplikasi berjalan?”, tetapi juga “apakah pengguna nyaman memakainya?”.

Contoh hasil sesi ini

Ketika tombol HITUNG diklik, Label hasil berubah menjadi “Aplikasi siap menghitung!”. Perhitungan lengkap akan lebih mudah dibuat jika struktur UI sudah benar.

Alur Belajar Hari Ini

Alur sesi ini dibuat bertahap. Pertama, kalian membuka materi di LMS dan memastikan App Inventor siap digunakan. Setelah itu, kalian melihat contoh tampilan aplikasi, membedakan UI dan UX, lalu mulai menyusun layout di Designer.

Bagian penting sesi ini adalah Layout Arrangement dan Asset Renaming. Arrangement membantu komponen tertata, sedangkan renaming membuat komponen mudah dikenali saat pindah ke Blocks.

Kenapa belum langsung menghitung?

Kalau tampilan belum jelas, logika hitung akan lebih sulit dites. Kita perlu memastikan layar sudah punya tempat input, tombol aksi, dan tempat output terlebih dahulu.

Di akhir sesi, project kalian belum harus menjadi kalkulator penuh. Namun, aplikasi harus sudah siap untuk dilanjutkan: komponennya lengkap, rapi, dan mudah ditemukan.

Persiapan Teknis

Sesi ini menggunakan LMS dan MIT App Inventor. Karena itu, pastikan browser, akun, dan koneksi internet berjalan dengan baik. Jika kelas memakai AI2 Companion, HP testing juga perlu siap agar tampilan aplikasi bisa dilihat secara langsung.

Persiapan teknis terlihat sederhana, tetapi sangat berpengaruh. Kalau akun belum masuk, halaman tidak terbuka, atau koneksi sering putus, proses membuat project akan terhambat.

Masalah Tampilan yang Sering Terjadi

Banyak aplikasi tidak gagal karena idenya buruk, tetapi karena tampilannya sulit digunakan. Pengguna bisa bingung ketika tombol terlalu kecil, teks tidak jelas, posisi komponen berantakan, atau urutan layar tidak mengikuti cara berpikir pengguna.

Pada project kalkulator, pengguna seharusnya langsung paham: ketik angka di TextBox, tekan tombol, lalu lihat hasil di Label. Kalau pengguna harus menebak-nebak, berarti UI perlu diperbaiki.

Contoh masalah UI

Tombol bertuliskan “OK” mungkin bisa dipakai, tetapi tombol bertuliskan “HITUNG” lebih jelas karena memberi tahu aksi yang akan dilakukan.

Di sesi ini, kalian belajar melihat tampilan dari sudut pandang pengguna, bukan hanya dari sudut pandang pembuat aplikasi.

Mengenal UI dan UX

UI adalah tampilan yang dilihat pengguna. Di App Inventor, UI dibuat di halaman Designer dengan komponen seperti Label, TextBox, Button, Image, dan Arrangement.

UX adalah pengalaman pengguna saat memakai aplikasi. UX terasa dari apakah user cepat paham, nyaman membaca, tidak salah klik, dan tidak perlu bertanya terlalu banyak.

Hubungan UI dan UX

UI yang rapi biasanya membantu UX menjadi lebih baik, tetapi tampilan yang menarik belum tentu nyaman digunakan. Aplikasi bisa terlihat bagus, tetapi tetap membingungkan jika alurnya tidak jelas.

Untuk project hari ini, UI yang baik berarti komponen tersusun jelas. UX yang baik berarti temanmu bisa mencoba aplikasi dan tahu langkah yang harus dilakukan tanpa penjelasan panjang.

Menilai UI dengan Alasan

Pada aktivitas ini, kalian tidak memilih berdasarkan warna favorit. Kalian menilai apakah tampilan mudah dipakai. Lihat urutan komponen, ukuran tombol, kejelasan teks, dan letak hasil.

UI yang baik biasanya memberi petunjuk tanpa harus dijelaskan. Judul memberi konteks, TextBox memberi tempat input, tombol menjelaskan aksi, dan Label memberi tempat output.

Contoh alasan yang kuat

“UI B lebih nyaman karena urutannya jelas: judul di atas, input di tengah, tombol setelah input, dan hasil terlihat di bawah tombol.”

Ketika membuat project sendiri, gunakan cara berpikir yang sama. Jangan hanya bertanya “bagus tidak?”, tetapi tanyakan “apakah pengguna paham cara memakainya?”.

Memisahkan UI dan UX

Developer perlu bisa membedakan bagian yang terlihat dan pengalaman yang dirasakan pengguna. Ini membantu saat memperbaiki aplikasi. Jika warna kurang kontras, itu masalah UI. Jika pengguna tidak tahu langkah berikutnya, itu masalah UX.

Keduanya saling terhubung. Misalnya, teks tombol yang jelas adalah bagian UI, tetapi efeknya membuat UX lebih baik karena user tidak perlu menebak fungsi tombol.

Cara mengecek

Tanyakan: “Apakah ini bentuk/teks/posisi yang terlihat?” Jika iya, itu UI. Tanyakan juga: “Apakah ini rasa nyaman/mudah/bingung saat memakai aplikasi?” Jika iya, itu UX.

Latihan sortir membantu kalian melihat bahwa aplikasi bukan hanya soal coding. Desain tampilan juga merupakan bagian dari cara aplikasi berkomunikasi dengan pengguna.

Mengenal Layout Arrangement

Di MIT App Inventor, Arrangement digunakan untuk mengatur posisi komponen. Tanpa Arrangement, komponen bisa terlihat menumpuk, jaraknya tidak konsisten, atau sulit dirapikan ketika jumlah komponen bertambah.

Vertical Arrangement cocok untuk susunan utama dari atas ke bawah, seperti judul, input, tombol, dan hasil. Horizontal Arrangement cocok untuk komponen yang ingin disejajarkan dari kiri ke kanan.

Analogi sederhana

Arrangement seperti kotak penyimpanan. Kalau semua barang ditaruh begitu saja di meja, meja cepat berantakan. Kalau barang dikelompokkan ke dalam kotak, semuanya lebih mudah dicari dan diatur.

Project Kalkulator Saku UI menggunakan Arrangement agar layar lebih rapi, konsisten, dan siap dikembangkan pada sesi berikutnya.

Memilih Arrangement yang Tepat

Pemilihan Arrangement bergantung pada arah susunan komponen. Jika kalian ingin komponen berurutan dari atas ke bawah, gunakan Vertical Arrangement. Jika komponen harus berdampingan dari kiri ke kanan, gunakan Horizontal Arrangement.

Untuk aplikasi kalkulator sederhana, Vertical Arrangement biasanya menjadi struktur utama. Komponen seperti judul, TextBox, tombol, dan Label hasil akan lebih mudah dibaca jika disusun dari atas ke bawah.

Contoh penggunaan

Gunakan Vertical Arrangement untuk kerangka halaman. Gunakan Horizontal Arrangement jika ingin menaruh dua tombol sejajar, misalnya HITUNG dan RESET.

Semakin jelas struktur layout, semakin mudah juga melakukan debugging saat tampilan tidak sesuai.

Urutan Komponen yang Mudah Dipahami

User biasanya membaca layar dari atas ke bawah. Karena itu, urutan komponen sebaiknya mengikuti alur berpikir pengguna: pahami judul, baca instruksi, isi input, tekan tombol, lalu lihat hasil.

Urutan yang rapi membantu UX. Jika Label hasil diletakkan terlalu jauh dari tombol, user mungkin tidak sadar bahwa hasil sudah berubah. Jika instruksi tidak ada, user bisa bingung angka apa yang perlu dimasukkan.

Alur ideal

Judul → Instruksi → TextBox → Button → Label hasil. Ini bukan satu-satunya desain yang mungkin, tetapi cocok untuk project awal karena sederhana dan jelas.

Saat membuat di Designer, gunakan urutan ini sebagai patokan agar project tidak hanya terlihat rapi, tetapi juga mudah digunakan.

Mengapa Komponen Perlu Direname?

MIT App Inventor memberi nama otomatis seperti Button1, Button2, TextBox1, atau Label3. Nama ini hanya menunjukkan urutan pembuatan, bukan fungsi komponen.

Saat project masih kecil, nama default mungkin terlihat tidak masalah. Namun, begitu komponen bertambah, kalian bisa salah memilih komponen di Blocks. Misalnya, ingin mengubah Label hasil, tetapi yang dipilih ternyata Label judul.

Efek saat debugging

Nama yang jelas membuat error lebih cepat ditemukan. Jika tombol tidak bekerja, kalian bisa langsung mencari btnHitung, bukan menebak-nebak Button1 atau Button2.

Biasakan rename sejak awal. Kebiasaan ini membuat project lebih rapi dan membantu kalian bekerja seperti developer sungguhan.

Aturan Naming yang Mudah Dibaca

Nama komponen yang baik biasanya singkat, konsisten, dan menjelaskan fungsi. Kalian tidak perlu menulis kalimat panjang sebagai nama komponen.

Pola yang umum digunakan adalah awalan jenis komponen + fungsi. Misalnya, btnHitung berarti komponen Button untuk menghitung. txtAngka berarti TextBox untuk memasukkan angka.

Bandingkan

Button1 tidak memberi informasi fungsi. btnHitung langsung memberi tahu bahwa tombol ini dipakai untuk aksi hitung.

Semakin konsisten penamaan kalian, semakin mudah project dibaca oleh diri sendiri, teman, dan guru.

Mengecek Nama Komponen

Latihan naming membantu kalian membiasakan pola pikir developer. Saat membuat aplikasi, kalian tidak hanya membuat sesuatu yang terlihat di layar, tetapi juga membuat struktur project yang mudah dibaca dari dalam.

Nama btnHitung lebih jelas daripada Button1 karena menunjukkan dua hal sekaligus: jenis komponennya Button, dan fungsinya untuk menghitung.

Cara memilih nama

  • Gunakan awalan sesuai jenis komponen.
  • Tambahkan fungsi utama komponen.
  • Hindari nama terlalu panjang.
  • Gunakan pola yang konsisten di seluruh project.

Kebiasaan ini akan sangat membantu pada sesi berikutnya, ketika jumlah Blocks semakin banyak.

Komponen yang Digunakan

Project ini menggunakan komponen dasar App Inventor yang sering muncul di aplikasi input-output: Screen, Label, TextBox, Button, dan Arrangement.

Screen1 adalah halaman utama aplikasi. Label dipakai untuk judul dan hasil. TextBox menerima input dari pengguna. Button menjalankan aksi. Arrangement menjaga tampilan tetap rapi.

Komponen dan fungsi

  • txtAngka: tempat mengetik angka.
  • btnHitung: tombol yang ditekan user.
  • lblHasil: tempat output ditampilkan.

Jika fungsi setiap komponen sudah jelas, kalian akan lebih mudah menyusun Blocks dan memperbaiki error.

Memahami Alur Aplikasi

Banyak aplikasi sederhana bekerja dengan pola Input → Proses → Output. Pengguna memberikan data, aplikasi memproses data tersebut, lalu aplikasi menampilkan hasil.

Pada Kalkulator Saku UI, input berasal dari TextBox, proses dimulai ketika Button diklik, dan output muncul pada Label. Walaupun belum menghitung angka secara lengkap, struktur ini sudah melatih cara berpikir aplikasi.

Contoh alur

User mengetik angka di txtAngka, menekan btnHitung, lalu lblHasil berubah menjadi pesan tertentu.

Jika kalian memahami alur ini, sesi berikutnya akan lebih mudah karena kalian tinggal menambahkan logika perhitungan di bagian proses.

Mengapa Perlu Wireframe?

Wireframe adalah sketsa susunan layar. Pada tahap ini, kalian belum perlu memikirkan warna, ikon, atau dekorasi. Fokusnya adalah posisi komponen dan alur penggunaan.

Untuk project ini, wireframe membantu memastikan semua bagian penting ada: judul, instruksi atau input, tombol, dan area hasil. Jika urutan dasarnya sudah jelas, pengaturan visual akan lebih mudah.

Fokus wireframe

Tanyakan: “Apakah user tahu aplikasi ini untuk apa?”, “Di mana user mengetik?”, “Tombol mana yang ditekan?”, dan “Di mana hasil muncul?”.

Wireframe yang baik mencegah kita menghabiskan waktu merapikan warna sebelum struktur utama benar.

Membangun Struktur di Designer

Langkah pertama di Designer adalah membuat wadah utama. Tambahkan Vertical Arrangement ke Viewer agar komponen utama tersusun dari atas ke bawah.

Setelah itu, atur properties penting seperti Width dan Alignment. Width membantu komponen mengikuti lebar layar, sedangkan Alignment membantu posisi komponen terlihat lebih rapi.

Jangan langsung menumpuk komponen

Jika semua komponen diletakkan langsung di Screen tanpa Arrangement, tampilan mungkin masih terlihat jalan, tetapi akan sulit dirapikan ketika project bertambah.

Struktur yang baik membuat project lebih mudah dikembangkan dan lebih mudah diperbaiki jika ada tampilan yang tidak sesuai.

Menambahkan Komponen Utama

Setelah wadah utama siap, tambahkan komponen yang akan dilihat dan digunakan oleh user. Komponen pertama adalah Label judul, lalu TextBox, Button, dan Label hasil.

TextBox sebaiknya memiliki Hint seperti “Masukkan angka”. Hint membantu pengguna mengetahui apa yang perlu diketik tanpa harus membaca instruksi panjang.

Text vs nama komponen

Button bisa bertuliskan HITUNG di layar, tetapi nama internalnya tetap btnHitung. User melihat Text, developer memakai nama internal.

Bagian ini penting karena App Inventor memisahkan tampilan yang dilihat user dan nama komponen yang dipakai di belakang layar.

Properties dalam App Inventor

Properties adalah pengaturan detail pada setiap komponen. Melalui Properties, kalian bisa mengubah teks, ukuran, lebar, posisi, warna, dan beberapa perilaku dasar komponen.

Untuk project ini, beberapa Properties yang paling penting adalah Text, Hint, Width, dan Alignment. Properti ini membantu aplikasi terlihat jelas dan nyaman digunakan.

Contoh

TextBox tanpa Hint terlihat seperti kotak kosong biasa. Dengan Hint “Masukkan angka”, user langsung tahu data apa yang harus dimasukkan.

Jangan hanya fokus pada warna. Pastikan setiap pengaturan membantu aplikasi menjadi lebih mudah dipahami.

Memahami Dua Jenis Nama

Di App Inventor, ada tulisan yang terlihat oleh user dan ada nama komponen yang digunakan oleh developer. Keduanya sering tertukar oleh siswa yang baru mulai membuat aplikasi.

Text adalah tulisan yang tampil di layar. Misalnya, tombol bertuliskan “HITUNG”. Sementara itu, btnHitung adalah nama internal yang dipakai saat memilih komponen di Blocks.

Kenapa ini penting?

Jika kalian hanya mengganti Text tombol menjadi “HITUNG” tetapi tidak rename komponennya, di Blocks tombol itu mungkin masih bernama Button1.

Biasakan mengecek keduanya: apakah tulisan yang dilihat user sudah jelas, dan apakah nama internal komponen sudah mudah dikenali.

Menyambungkan UI ke Blocks

Designer membuat tampilan aplikasi. Blocks membuat aplikasi merespons tindakan pengguna. Pada sesi ini, kalian menggunakan event sederhana: ketika tombol diklik, aplikasi mengubah teks pada Label hasil.

Event yang digunakan adalah konsep Button.Click. Artinya, perintah di dalam event hanya berjalan ketika pengguna menekan tombol tersebut.

Kenapa pakai event sederhana?

Karena fokus sesi ini masih UI. Kita hanya perlu mengecek bahwa tombol yang dibuat di Designer bisa dikenali di Blocks dan dapat mengubah Label yang benar.

Jika event dasar sudah berhasil, kalian siap menambahkan logika perhitungan pada sesi berikutnya.

Membaca Pseudocode Sebelum Blok

Pseudocode adalah cara menuliskan logika program dengan bahasa sederhana. Bentuknya belum seperti blok App Inventor, tetapi membantu kalian memahami alur sebelum menyusun blok asli.

Dalam project ini, logikanya pendek: ketika tombol Hitung diklik, ubah teks Label hasil. Dengan alur sederhana ini, kalian bisa mengecek apakah komponen sudah terhubung dengan benar.

Yang akan terjadi

Sebelum tombol diklik, Label hasil bisa bertuliskan “Hasil muncul di sini”. Setelah tombol diklik, Label berubah menjadi “Aplikasi siap menghitung!”.

Bagian screenshot blok sengaja dibuat placeholder agar bisa diganti dengan gambar blok App Inventor asli dan tampilannya tetap sesuai platform.

Testing Event

Testing dilakukan untuk memastikan aplikasi merespons sesuai rencana. Jika tombol ditekan, Label hasil harus berubah. Jika tidak berubah, berarti ada bagian yang perlu dicek.

Dalam testing, jangan langsung menghapus semua komponen. Cek satu per satu: apakah tombol yang dipakai benar, apakah event dipasang pada tombol yang tepat, dan apakah output diarahkan ke Label yang benar.

Urutan cek cepat

  1. Cek nama tombol: btnHitung.
  2. Cek event: when btnHitung.Click.
  3. Cek target output: set lblHasil.Text.
  4. Cek teks output yang ingin ditampilkan.

Testing kecil seperti ini membantu kalian menemukan error sebelum project menjadi lebih besar.

Live Testing Tampilan

Testing di layar komputer dan testing di HP bisa terasa berbeda. Aplikasi yang terlihat rapi di komputer belum tentu nyaman di layar HP jika ukuran atau jaraknya kurang pas.

AI2 Companion membantu kalian melihat aplikasi secara langsung di HP. Dengan begitu, kalian bisa mengecek ukuran tombol, posisi TextBox, dan keterbacaan Label dari sudut pandang pengguna.

Yang perlu dicek saat live testing

  • Apakah tombol mudah ditekan?
  • Apakah TextBox mudah ditemukan?
  • Apakah teks terlihat jelas?
  • Apakah hasil muncul di tempat yang mudah dilihat?

Jika live testing belum digunakan di kelas, kalian tetap bisa melakukan pengecekan dari preview App Inventor dan diskusi dengan teman.

Melakukan Peer Test

Peer test adalah saat teman mencoba aplikasi kalian. Tujuannya bukan mencari siapa yang paling bagus, tetapi menemukan bagian tampilan yang masih membingungkan.

Saat teman mencoba, jangan langsung menjelaskan semuanya. Amati apakah temanmu bisa menemukan input, tombol, dan hasil secara mandiri. Jika temanmu bingung, itu tanda UI atau UX perlu diperbaiki.

Pertanyaan untuk tester

“Menurutmu, apa yang harus diketik?”, “Tombol mana yang kamu tekan?”, dan “Di mana hasilnya muncul?”

Masukan dari tester membantu kalian melihat aplikasi dari sudut pandang pengguna, bukan hanya pembuat aplikasi.

Cara Debugging Sesi Ini

Debugging pada sesi ini tidak hanya tentang blok. Tampilan juga bisa memiliki masalah: komponen berantakan, urutan tidak jelas, nama komponen membingungkan, atau tombol tidak mengubah output.

Gunakan cara cek satu per satu. Jika tampilan berantakan, cek Arrangement dan Properties. Jika Blocks membingungkan, cek nama komponen. Jika tombol tidak merespons, cek event dan target output.

Jangan panik saat error

Error bukan tanda gagal. Error adalah petunjuk bahwa ada bagian yang perlu diperiksa. Cek dari struktur paling besar dulu, baru masuk ke detail.

Kebiasaan debugging yang rapi akan berguna di semua sesi berikutnya.

Kriteria Project Berhasil

Output minimum adalah target utama yang perlu selesai. Jika target ini belum terpenuhi, jangan terburu-buru menambahkan fitur baru atau dekorasi tambahan.

Project dianggap berhasil jika komponen sudah lengkap, layout menggunakan Arrangement, nama komponen jelas, tombol dapat diklik, dan Label hasil berubah sesuai perintah.

Ukuran keberhasilan

Orang lain bisa melihat aplikasimu dan memahami alurnya tanpa penjelasan panjang: ketik angka, tekan tombol, lihat hasil.

Jika semua checklist sudah selesai, project kalian sudah siap menjadi dasar untuk sesi berikutnya.

Mengembangkan Project Setelah Target Utama

Challenge tambahan boleh dikerjakan jika output minimum sudah selesai. Tantangan ini melatih kalian meningkatkan tampilan tanpa mengorbankan kejelasan aplikasi.

Jika menambahkan ikon, pastikan ikon tidak menutupi input, tombol, atau hasil. Jika menambahkan tombol Reset, pastikan nama komponennya jelas, misalnya btnReset.

Ide reset

Ketika btnReset diklik, TextBox kembali kosong dan Label hasil kembali ke “Hasil muncul di sini”.

Ingat, dekorasi harus membantu tampilan, bukan membuat aplikasi semakin sulit dipakai.

Menyimpan dengan Nama yang Jelas

Nama project yang jelas membuat project mudah ditemukan pada sesi berikutnya. Hindari nama seperti “Project Baru”, “Coba-coba”, atau “Untitled”.

Gunakan nama yang menunjukkan isi project dan pemiliknya. Contohnya, KalkulatorSakuUI_Rafa atau KalkulatorSakuUI_Nadia.

Sebelum keluar

Pastikan project sudah muncul di daftar My Projects. Jika belum yakin, minta bantuan guru untuk mengecek.

Project ini akan menjadi dasar untuk sesi berikutnya, jadi pastikan tidak hilang atau tertukar dengan project lain.

Menutup Sesi

Hari ini kalian tidak hanya membuat tampilan aplikasi, tetapi juga belajar berpikir seperti developer. Developer perlu memikirkan struktur komponen, nama internal, tampilan yang dibaca user, dan pengalaman saat aplikasi digunakan.

Kalian juga sudah menghubungkan satu event sederhana di Blocks. Walaupun belum membuat kalkulator penuh, kalian sudah menyiapkan pondasi penting: input, tombol aksi, dan output.

Yang dibawa ke sesi berikutnya

Project Kalkulator Saku UI yang sudah rapi akan lebih mudah dikembangkan menjadi aplikasi yang benar-benar memproses input.

Simpan project dengan baik, karena pekerjaan hari ini akan menjadi dasar untuk belajar logika aplikasi berikutnya.
